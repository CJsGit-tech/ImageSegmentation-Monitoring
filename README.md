## 圖像分割與眼距量測 （相關假設）

- 輸入資料:
    - 靜態的 COCO val2017 圖片, 每張至少有 2 隻動物. 此專案的量測對象為 **貓與狗**.

- 不微調模型: 
    - 預設是 PoC 專案, 目標放在探索開源專案中是否有可行的思路
    - COCO 沒有**眼睛類別**, 因此僅使用預訓練模型可導致準確率不足

- 眼睛歸屬:
    - 圖片中的動物皆以正面朝前.
    - 右眼定義:
        - 假設動物臉朝鏡頭且頭部直立因此取影像中 x 較小的眼睛
        - 側臉時可能判斷錯誤.

- 眼睛距離定義:
    - 兩個劃定的眼睛的圓圈之中心點, 使用歐氏距離, 單位為影像像素, 同時換算並推估公分(cm)
    - 量測條件
        - 一隻動物要有 2 個眼睛才量測雙眼距離並區分左右
        - 右眼距離需要至少 2 隻這樣的動物, 並計算每一對
        - 不校正頭部轉向與動物離鏡頭的遠近, 因此結果不等於實際的距離

- 驗證可行性
    - 準確度以 3 張測試圖的眼睛標記為基準. 參數也是依這 3 張圖調整的.
    - 有附上其他 9 張測試圖片, 當作 PoC 可行性之評估.

## 即時資料分析與監控系統 （相關假設）

- 資料模型:
    - 假設**應用場景為設備感測器讀數**
    -  一筆記錄代表某個分類在某個時間點的一次讀數. 
    - 以「分類」區分設備或指標, 沒有獨立的設備欄位, 可以自由設定新設備與讀數
    - 導入資料的時間戳需含時區資訊 (UTC 為主) 未填時以導入時間為準.
    - 系統日誌預設保留 365 天.

- 資料來源: 
    - 沒有串接真實設備, 由後端模擬 4 個設備 (溫度、壓力、馬達轉速、振動)
    - 預設每秒各產生一筆, 其中約 5% 刻意超出範圍以展示異常.
    - 歷史查詢單次最長 3 個月, 假設更長的期間可分段查詢.
        - 避免服務器負擔也預防大量的導出行為
    兒

- 異常判斷:
    - 數值小於等於最小值或大於等於最大值即為異常, 碰到邊界也算. 
    - 異常數據的最大／最小可以自行設定, 尚未設定範圍的分類不判斷.
        - **範圍由 Admin賬號依分類設定, 只影響之後的判斷, 已保存的記錄不回頭重判.**
    - 為了事後可追查, 異常記錄一律唯讀 (包含 Admin), 即使當初填錯也無法更正.
    
- 帳號管控：
    - 註冊不需核准, 新帳號一律為 Viewer, 由 Admin 調整權限. 

- 批量導入:
    - 檔案視為一個整體, 有任何一列錯誤就全部不寫入. 上限為 5 MB、10,000 列. 
    - 重複上傳只以檔名判斷, 不比對內容.


## 開發方式 （以實時監控平台為例）

監控系統的工作以 [LinearBoard](https://github.com/CJsGit-tech/LinearBoard) 管理. 

這是我開發的本機專案管理工具, 用來協調我與 AI Agent 之間的工作. 

需求、決策、任務與驗證證據都存放在本地的管理專案服務器. 可幫助在我與Agent在協作中保持目標的一致性.

### 開發流程

| 階段 | 做法 | 產出 |
|---|---|---|
| **1. 規劃** | 先釐清題目與要解決的問題, 再寫成願景文件 | 願景文件 |
| **2. 里程碑** | 由願景推導使用者故事, 再依成果分組 | 里程碑 M1 到 M5 與分組的使用者故事 |
| **3. 需求** | 為每個里程碑撰寫 PRD, 逐一釐清會影響使用者行為或測試方式的規則 | PRD 與[決策問答頁](monitoring-application/docs/MonitoringDashboard-decision-qa.html) |
| **4. 設計** | 比較版面方向, 選定後製作完整畫面供審閱 | 設計規格與設計審閱圖庫 |
| **5. 任務** | 將需求與設計拆成前端與後端任務, 再依相依性排成批次 | 連回 PRD 的任務與批次 |
| **6. 交付** | AI Agent 依批次實作, 再由實作者以外的審閱者操作實際系統並記錄證據 | 程式碼、驗證紀錄與[瀏覽器測試](monitoring-application/e2e/README.md) |

**我與 AI Agent 的分工:**

- 我負責決定: 
    - 每個階段由我進行大方向的規劃. 並梳理專案中可能遺漏的一些設置或應該做的假設
    - 專案的開發在取捨與設計核准都由我決定
    - 特別是針對里程碑的制定上主要由我這邊決定實施範圍
    - 需求變更：
        - 開發中確認的變更要更新到對應的 PRD, 影響多筆紀錄時, 先預覽修改內容.
        - 經我核准後才更新. 驗收時發現的問題則記錄為有來源連結的修復任務.

- AI Agent 負責執行與提問
    - AI Agent 依指令撰寫文件與實作, 遇到會影響產品行為的問題時會停下指出不自行假設

註記： 圖像分割屬於實驗性質, 是透過多輪實驗比較方法, 過程記錄於[封存實驗](image-segmentation/experiments/outputs/experiments/archive/README.md).
